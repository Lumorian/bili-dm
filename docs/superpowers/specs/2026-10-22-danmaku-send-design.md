# 悬浮窗发弹幕(仿官方弹幕姬)

- 日期:2026-10-22
- 状态:已实现
- 目标:在既能看弹幕、也能发弹幕上对齐 B 站官方弹幕姬;发送入口就放在弹幕面板底部,
  不另开窗口、不弹对话框。

## 1. 官方做法(照抄的部分)

官方直播间面板(`chat-history-panel`)底部是一条输入条:圆角输入框 + 右侧发送按钮,
普通用户 20 字上限,回车发送,发出去的那条**立刻出现在列表里**(不等服务端回推)。
> 注:输入条的具体 CSS 类名未随本次改动核对(2026-10 抓取线上页面时样式表未取回),
> 故本文只对齐**交互与度量**(20 字、回车、右侧按钮、贴卡片底边),不声称逐像素一致。
接口是 `POST https://api.live.bilibili.com/msg/send`,表单字段:

| 字段 | 值 | 说明 |
|------|-----|------|
| `roomid` | 真实房间号 | 短号要先 `GET /room/v1/Room/get_info` 换一次 |
| `msg` | 正文 | 20 字上限 |
| `color` | 16777215 | 白色(官方默认) |
| `fontsize` | 25 | 「标准」档 |
| `mode` | 1 | 滚动弹幕 |
| `csrf` / `csrf_token` | cookie 里的 `bili_jct` | 两个字段值相同 |
| `rnd` | 时间戳 | 官方随手防缓存 |

请求还必须带登录 cookie(`SESSDATA`)。没有登录态 B 站只回 `{"code":-101,"message":"账号未登录"}`;
只有 `SESSDATA` 没有 `bili_jct` 则回 `-111`。

## 2. 本项目定下的几件事

### 2.0 发到哪个房间:不许额外配置

房间是 dmnotifier 订阅的,overlay 只是收。用户完全可以没有任何 `--room` / `rooms` 配置
却在正常看弹幕(dmnotifier history 里就订阅着),此时拦一句"先在设置里添加直播间"是没道理的
——**能看就能发**。房间来源按确定性排序:

1. per-room 模式的 `room_filter`(窗口绑死的房间;发错房间比发不出去更糟);
2. `config.yaml` 的 `rooms`(用户明确配过的;合并模式优先 B 站房间);
3. **正在流动的弹幕**带来的 `platform:rid`(收到它本身就是可用性证明);
4. dmnotifier `config.yaml` 的 `history`(刚启动、一条弹幕还没来时的兜底)。

合并模式会同时收到多个房间,所以 3 不能"跟着最后一条弹幕跳":已定下 B 站房间就不再改,
别的平台来的 B 站房间可以顶替(`sender.pick_observed_room`,纯逻辑带测试)。

### 2.1 cookie 从哪来

发送必须带登录态,而订阅时本来就带着它。取值顺序(前者优先):

1. `--room bilibili:689422:<cookie>` 里的 cookie;
2. `config.yaml` 的 `send_cookie`(单独给发送用;设置对话框里可填,密码框显示);
3. dmnotifier `config.yaml` 的 `history` 中该房间那条的 cookie——能收到弹幕就说明它活着。

### 2.2 能在本地判断的错误,不要打网络

缺 `bili_jct`、正文为空/超长、房间不是 B 站——这些在按下发送那一刻就能说清,输入条里
就地给出原因(而不是让用户对着一个 `-111` 猜)。缺 csrf 的提示要点明**看弹幕不用登录、
发弹幕才要**,否则"我能看却不能发"看起来就像 bug(这是实测踩到的第一个疑问)。
缺 csrf 的判定放在 `sender.send()` 与界面两侧:前者保证库被别处调用时也安全,后者给出
更具体的引导。

### 2.3 回显与去重

发送成功后立刻本地插一行(官方同样即时上屏)。但 WebSocket 会把同一条弹幕推回来,
不去重就会每条显示两遍。去重规则:

- **登记发生在「按下发送」那一刻**,不是「确认成功」——服务端广播可能比 HTTP 响应先到;
- 匹配靠"正文 + 自己的 uid + 时间窗",uid 在拿到 `nav` 身份后回填;
- 期望 8 秒过期:回推可能压根不来(ws 断线),过期后同内容的正常弹幕照常显示;
- 发送失败或被节流时**撤掉期望**,免得它误吞后来一条内容相同的正常弹幕。

### 2.4 键盘:layer-shell 表面默认收不到按键

`make_overlay()` 把表面设成 `KeyboardInteractivityNone`(kotonoha 是给歌词条用的),
所以**不解锁就永远打不进字**。解锁(可交互)时经桥的 `set_keyboard_interactivity` 打开,
锁定(穿透)时关掉——锁定态整块窗口在往外放行鼠标,这时抢键盘只会顶掉用户正在打字的窗口。

kotonoha 的 `OverlayPlatform` 协议还没暴露这项,因此 `keyboard.py` 按"适配器方法 →
桥直调 → 什么都不做"三级退让;三级都不成立(普通顶层窗/X11/offscreen)本来就是普通窗口,
自然收键盘。

### 2.5 节流与线程

B 站大约 1 条/2s,本地先按 1.5s 节流挡住连点,不靠风控回 `-412` 才发现。发送是同步
`urllib`(与 `api.py` 同风格),必须扔进 `QThreadPool`——主线程被一次 5s 超时卡住就等于
166 帧重绘丢掉。结果经信号回主线程,界面只在主线程改。

## 3. 落地位置

| 文件 | 职责 |
|------|------|
| `sender.py` | `msg/send` 调用、短号解析、`nav` 身份、cookie/csrf 提取、错误码中文化(纯逻辑 + urllib) |
| `submit.py` | 节流、后台线程、结果信号、身份缓存 |
| `danmaku/echo.py` | 回显去重(纯逻辑) |
| `danmaku/composer.py` | 输入条 UI(20 字上限、字数、回执、锁定态只读) |
| `keyboard.py` | 层壳键盘交互开关(三级退让) |
| `window.py` | 接线:输入条贴在卡片底部、发送流程、锁定态联动、本地回显 |
| `settings.py` | 启用开关 + 发送 cookie(含 bili_jct 检查提示) |
